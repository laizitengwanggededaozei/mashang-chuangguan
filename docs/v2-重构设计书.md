# JavaQuest v2 重构设计书（需求拆解 / 问题诊断 / 新架构 / v2.0→v2.2 迭代记录）

> 角色：游戏架构设计师 + 软件工程专家
> 输入：用户对 v1 的否定性反馈
> 结论：v1 的**内容模型**与**判题核心**都不成立，需要重做内容层与引擎层，保留外壳（本地零依赖、可存档、章节对应黑马课程）。

> 本文档按时间顺序记录：第一~四章是 v2.0 的设计与实施；第五章是 v2.1 玩法层；第六章是 v2.2 内容打磨；第七章是**当前交付状态与验收矩阵**。

## 一、把用户发言拆成可执行需求（需求分解）

| 编号 | 原始诉求 | 工程化需求 | 验收标准 |
|---|---|---|---|
| R1 | “不应该存在问答题” | 题库**只保留编程题**；选择题/填空/排序/输出预测全部下架 | 数据层不存在 `choice/multi/fill/order/output` 题型；前端无选择题渲染路径 |
| R2 | “编码题太简单都是打印题” | 题目必须**要求实现逻辑**（方法/类/算法），而非“把字打出来” | 判题入口以**反射调用方法/类**为主（method/design 模式），`System.out.println("hello")` 类题目为零 |
| R3 | “具有真正难度、对计算机有理解深度” | 题目覆盖：复杂度、边界、数据结构选型、递归/回溯、状态机、内存与引用语义、设计模式、并发/不可变性 | 每题带 `tags`；≥60% 题目需要算法或结构设计；T5 层为系统设计题 |
| R4 | “不再依据难度划分，而是每章按递进难度顺序” | 取消“简单/中等/困难”标签；改为**章节内关卡序号 = 递进顺序**（第1关→第N关），难度由知识依赖+隐藏用例强度体现 | 关卡按 `order` 单调递增解锁；无难度标签字段 |
| R5 | “最难的应当是创新的、具有计算机思维、考察知识体系的” | 每章末关为**创新/系统设计题**（如实现 LRU、Trie、表达式求值、迷你状态机、调度器、不可变容器） | 每章至少 1 题 `design`/`stress` 模式 |
| R6 | “完全翻新题库” | v1 题库整体归档，重建 14 章 × 5 阶段的新题库 | 旧文件移入 `待审核备份/`，新题库每章 ≥15 题且全部通过自动验证 |
| R7 | “编译器核心需要重新完善，现有能力不足” | 重写判题核心：多文件编译、逐用例进程隔离、TLE/MLE/RE/CE/WA 判决、比较器库、隐藏用例、**随机对拍压力测试** | 新核心通过自测矩阵（8 类判决全部可复现） |
| R8 | “重新设计游戏难度、章节构建” | 章节 = 知识域；关卡 = 递进；章末 = Boss（创新题）；XP 按阶段权重 | 进度门控正确；Boss 需前置全通 |
| R9 | （既有约束）删除必须备份 | 所有下架内容移入 `待审核备份/`，不物理删除 | 备份目录含 v1 全量归档，输出待删清单 |

## 二、v1 现存问题诊断（根因分析）

### P1 内容层：题型比例错误导致“游戏=选择题”
- v1 题库实测（整理文档时对归档文件递归统计）：**问答类 1722 条**撑规模，**编码题仅 481 道，且 481 道全部含 `System.out.print`** → 用户感知为“做题软件”“都是打印题”。

  | v1 题型 | 条数 |
  |---|---|
  | choice（选择题） | 648 |
  | output（输出预测） | 423 |
  | fill（填空） | 293 |
  | multi（多选） | 214 |
  | order（代码排序） | 144 |
  | **问答类合计** | **1722** |
  | coding（编程题） | 481（含 `System.out.print` 的占 481/481 = 100%） |

  > 本节早期写作“1708 道选择题”，是未核实的估算；上表为对 `待审核备份/v1-问答版-题库/` 的实测统计结果。
- **根因**：把“知识点覆盖量”当成“游戏深度”，用低成本题型堆数量。

### P2 判题核心：只有“编译 + stdout 比对”
- 仅支持整程序 stdin/stdout；无法考“实现一个方法/一个类”。
- 无 TLE/MLE/RE 判决，无比较器（浮点/无序/多解），无隐藏用例，**无随机对拍** → 可被硬编码答案绕过，也无法承载算法题。
- **根因**：把 judge 当 IO 工具而非“评测系统内核”。

### P3 难度模型：标签化而非递进
- v1 难度只是文字标签，关卡内部题目无知识依赖顺序，缺乏“能通关=能力达标”的保证。

### P4 数据组织：章节/小节粒度与游戏节奏不匹配
- 148 小节 × 10 题 = 碎、平、无节奏；玩家无法感知成长曲线。

### P5 工程隐患（v1 已暴露）
- 数据文件由多方并发追加写坏（ch11/ch13 出现半截文件）；
- 引擎合并同 key 数据时曾覆盖（已修）；
- 静态服务器与判题服务同进程，重启才生效（已暴露 404）。

## 三、新架构设计

### 3.1 评测内核 v2（`tools/judge-core.mjs`）

```
提交 {problemId, code}
   │
   ├─ 编译层: Main.java (+ Harness.java / Gen.java / Ref.java)  → javac -encoding UTF-8
   │     失败 → CE(含 javac 原始诊断)
   │
   ├─ 执行层: 每个用例独立 JVM 进程
   │     java -Xmx<mem>m -cp dir Harness <caseIdx> <args...>
   │     看门狗线程 halt(124) → TLE
   │     OutOfMemoryError → MLE
   │     非零退出/异常栈 → RE
   │
   ├─ 比较层: exact | tokens | float:eps | unordered | set | lines
   │
   └─ 判决: CE > TLE > MLE > RE > WA > AC（逐用例），汇总得分
```

四种题目模式：

| 模式 | 适用 | harness 行为 |
|---|---|---|
| `method` | 实现方法（主流） | 反射调用 `Main.solve(...)`，入参按类型从 token 解析，返回值规范化序列化后比对 |
| `design` | 系统设计题（LRU/Trie/MinStack…） | 按操作序列 `["LRUCache","put","get"]` 反射构造/调用，逐操作比对输出数组 |
| `stress` | 算法题防硬编码 | 由题目自带 `Gen`(随机生成器) + `Ref`(暴力/参考实现) 对拍 N 次，输出不一致即失败并打印反例 |
| `stdin` | 少量 IO 型题（兼容保留） | 运行 `Main` 并喂 stdin（仅当题目确实需要） |

支持参数/返回类型：`int,long,double,boolean,char,String,int[],long[],double[],boolean[],char[],String[],int[][],String[][],List`

隐藏用例：题目 `tests` 中 `hidden:true` 的用例**只存在于服务端**，客户端只能拿到公开样例 → 防止“对着样例打表”。

### 3.2 内容模型 v2

```js
{
  id: "ch04-L07", ch: 4, order: 7,            // order = 递进序号（唯一难度标尺）
  title: "滑动窗口求最长无重复子串",
  stage: "算法深潜",                            // 阶段名（非难度标签）
  tags: ["滑动窗口","哈希表","O(n)"],
  q: "...题干：输入输出契约、边界要求、复杂度要求...",
  mode: "method",                              // method | design | stress | stdin
  entry: { method: "solve", params: ["String"], ret: "int" },
  starter: "public class Main { ... // TODO ... }",
  solution: "...参考实现（服务端保存，用于对拍与提示）...",
  tests: [ {name:"样例1", args:["abcabcbb"], expect:"3", cmp:"exact"},
           {name:"边界", args:[""], expect:"0", cmp:"exact", hidden:true} ],
  stress: { iterations: 300, gen:"java代码", ref:"java代码" },   // 可选
  hints: ["滑动窗口维护窗口内字符最后位置"]
}
```

### 3.3 章节与递进体系（14 章 × 5 阶段）

| 阶段 | 主题 | 认知目标 | 典型形态 |
|---|---|---|---|
| 第1阶段 基础语感 | 变量/运算/分支/循环/数组/方法 | 把“会写”变成“写对” | method 模式小函数，含边界 |
| 第2阶段 组合运用 | 字符串/集合/二维数组/对象 | 多步拆解 | method + 多类型返回 |
| 第3阶段 综合拆解 | 递归、排序、双指针、前缀和 | 结构化解题 | method + 隐藏用例 |
| 第4阶段 算法深潜 | 动态规划、图/树、堆、并查集 | 复杂度意识 | method + **stress 对拍** |
| 第5阶段 创新挑战 | 设计题：缓存/解析器/状态机/调度 | 计算机系统思维 | **design** + 操作序列；**末关为章节 BOSS**（限时 + 公开/隐藏双阶段） |

章节 Boss = 第 5 阶段末关（L15），需本章前 14 关全通才解锁；v2.1 起 BOSS 不再是"更难的一关"，而是**限时 10 分钟 + 多阶段**的独立形态（见第五章）。

### 3.4 前端 v2
- 关卡地图（章节 → 阶段 → 关卡，递进解锁）

- 判题与静态服务同进程但**热加载**题库文件；
- 所有下架内容移入 `待审核备份/`。

## 五、v2.1 玩法层升级（成就徽章 + BOSS 限时多阶段）

v2.0 把"判得准、教得会"做透了，但表层只是"带锁的题库"。v2.1 补齐玩法层。

### 6.1 章节 BOSS：从"更难的一关"变成"限时多阶段挑战"

原来 L15 与普通关只差难度，没有形态区别。现在：

- **限时**：进入关卡即开始 10 分钟倒计时（`Q.BOSS_SECONDS`），倒计时条在最后 60 秒变红；超时**不判负**，返回地图重进即重新计时，但提交次数保留（避免惩罚性体验）。
- **多阶段**：判题被拆成两个阶段——阶段 1 是题面公开的操作序列，阶段 2 是一条**学生看不到的隐藏边界序列**。前者验证"能按题面跑通"，后者验证"边界是否真的想过"。
- **判定**：两阶段全通过才算击破 BOSS；通关记录用时与提交次数，XP 额外 +80。
- **14 条隐藏边界序列**全部按章定制：容量为 1 的 LRU、`MIN_VALUE` 再减 1 回绕到 `MAX`、空状态聚合返回值、删除中间元素后的换位、38 位除 20 位、部分未占用的 `free` 必须整段拒绝、`"-0..0"` 规范化、审计阈值等值边界、`dmg<=0` 无副作用、一击致死时跳过敌方回合、10^21 平方……

判题内核的 `opSets` 结构天然支持这件事（`tools/judge-core.mjs` 早已按 `opSets[setId]` 索引类型声明），v2.1 只是把它用起来。

### 6.2 成就徽章（12 枚）

`js/engine2.js` 的 `Q.BADGES` 是声明式表，每项一个 `test()` 谓词，`Q.checkBadges()` 在通关结算时统一判定并持久化：

初次编译 / 首章通关 / 三章连破 / 十四柱 / 一击必杀 / 十连完美 / 算法深潜者（通过全部 42 个随机对拍关）/ 架构使徒（全部 42 个设计关）/ BOSS 终结者 / BOSS 全破 / 稳如老狗（同一关失败 20 次后拿下）/ 全量通关。

- 新增存档字段：`best`（最快用时）、`streak`（首提交连击，含 `best`）、`boss`（BOSS 战绩）、`attempts`（每关提交次数），并对旧存档做字段补齐（向后兼容）。
- 解锁时右下角弹出成就提示，HUD 显示 `🏅 已解锁/总数`，战绩页有徽章墙与 BOSS 进度条。

### 6.3 新增护栏：前端冒烟测试

`tools/ui-smoke.mjs` 用 stub DOM **真实执行** `api.js` / `engine2.js` / `ui2.js`，覆盖地图渲染、每章第 1 关可点/其余锁定、开卡、提交判定、徽章解锁、BOSS 多阶段与计时器启动。

它存在的直接原因：v2.0 上线后用户反馈"点击第一关没反应"——模板里调 `JQ2UI.open(id)`，代码里却只定义了 `openLevel`，点击等于调用不存在的函数。**这类接线故障编译器抓不到、题库校验也抓不到**，只能靠执行渲染路径发现。同一轮还加了两条能在将来拦住同类问题的题型门禁：

- design 的 `tests` 不会被执行 ⇒ 禁止用 `tests` 冒充公开样例；
- 判题会调用的**每个方法名必须在题干里出现** ⇒ 杜绝"按题面写却必然失败"的关卡；
- BOSS(L15) 必须有 `opSets`（公开 + 隐藏）且每组 `ops`/`expect` 等长。

### 6.4 修复的真实缺陷

| 缺陷 | 性质 | 处置 |
|---|---|---|
| `JQ2UI.open` 未定义 | 点击地图无反应（用户上报） | 补 `Q.open` 别名，并加冒烟测试 |
| stress 关丢弃作者手写用例 | 184 条用例（96 隐藏）从不执行，边界错误被判 AC | 改为真正执行 |
| 上述死用例中 **11 处错误期望值** | 从未执行所以无人发现 | 三方比对（解/独立 Ref/手写期望）+ 人工核对后修正 |
| ch11-L11 溢出饱和 | 参考实现先 int 溢出再饱和，饱和值错误 | 改为 long 域计算 |
| ch13-L12 榜单方向 | 手写测试数据用了降序，与题面/Gen 的升序矛盾 | 修正测试数据，保留原解 |
| ch02-L11 与 ch01-L03 同题 | 跨章重复且是全章最简单 | 重写为"统计 [0,n] 二进制 1 总数"（按位计数） |

**未删除任何文件**：全部改动均以"修正"或"移动到 `待审核备份`"完成。

## 六、内容打磨（v2.2）

### 7.1 方法：先量化，再动手

`tools/content-audit.mjs` 做三件事：解法指纹比对（归一化去注释/空白/`java.util.` 前缀/修饰符后逐一比对）、跨章接口签名统计、章内参考实现规模分布。

**一个重要的方法论教训**：最初我把"参考实现字符数短"当作难度倒挂的代理指标，结果报了 8 处告警，逐条核对后发现**其中 5 处是误报**——ch02-L12（位运算加法）、ch05-L10（阶乘取模）、ch06-L11（别名安全区间替换）的解法确实只有一百多字符，但它们考的是位运算进位、取模防溢出、原地更新的别名语义，是真正的"短而难"。字符数不是复杂度的好代理。

所以最终只对**逐对核对题干与解法后确认的同题**动手。

### 7.2 消除的跨章同题（5 处）

| 关卡 | 原题 | 与谁重复 | 改为 |
|---|---|---|---|
| ch04-L07 | 前缀和区间查询 | ch03-L10（同一道题） | 定长窗口最大和（滑动窗口，O(n) 增量维护） |
| ch07-L02 | 删除指定值 | ch04-L04（同题，仅顺序要求不同） | 交换法无序就地移除（与保序快慢指针形成对照） |
| ch08-L11 | 比较器排序 | ch11-L10（高度重合） | 字符串比较器的平局与传递性（长度→字典序→稳定） |
| ch07-L10 | 数组中第 k 大 | ch01-L11（同题，且解法仅 `Arrays.sort`，无深度） | 滑动窗口内第 k 大（增量维护有序容器，暴力排序会超时） |
| ch02-L05 | 闰年与月份天数 | ch03-L01（同题） | 短路求值与按位/逻辑运算语义（含 `>>` vs `>>>`、位移取模 32） |

### 7.3 补强的随机对拍覆盖面

ch02-L12 / ch05-L10 / ch06-L11 的解法虽短但难，可原来它们的 `Gen` 随机数据太窄（ch05-L10 只测 n≤40，O(n²) 写法也能过）。现在：

- ch02-L12：5 种分布（全域随机 / 小值 / 极值组合 / 边界加小量 / **相加得 0 使进位链最长**）
- ch05-L10：去掉塞进随机循环的大规模迭代（会累积超时），把"n=1e5 必须 O(n)"改为**固定用例独立 JVM** 考核；随机部分覆盖特殊模数（1、2、3、1e9+7、999999937）
- ch06-L11：覆盖负值 / 密集小值（前驱更新会连成一片）/ `INT_MIN` / 上界 5000

### 7.4 新增门禁：防同题回归

`tools/verify-problems.mjs` 增加两条单章内检查：**标题不得重复**、**解法指纹不得完全相同**。跨章比对留给 `content-audit.mjs`（需要全局视野）。

### 7.5 本轮发现的自身错误（如实记录）

写期望值和使用工具时我自己犯了 5 次错，全部靠自检拦下：

1. ch04-L07 全负窗口期望写成 `-3`（正确 `-6`：窗口为 -6/-10/-11）
2. ch08-L11 `String[]` 期望没加引号（`Ser` 输出是 `["a","cc"]`）
3. ch07-L10 全负窗口期望写成 `[-1,-1]`（正确 `[-5,-2]`）
4. ch02-L05 `(6|3) & ~6` 期望写成 `3`（正确 `1`：`7 & -7 = 1`）
5. ch07-L10 大规模用例塞了 99501 个返回值，把命令行参数撑爆导致 RE

第 5 条尤其说明**"测试数据本身也要受约束"**：判题通过命令行参数传参，返回值过大就会超出系统限制。现已把该用例缩到 4001 个窗口（参数约 22KB），既能拉开与暴力排序的复杂度差距，又不会撑爆参数。
